# staff-admin: Keycloak permissions and blast radius

`staff-admin` is an internal service (no published port; backend network only, reached through
the gateway at `/api/staff/**`). It manages the agent accounts of one tenant site at a time,
always taken from the caller's own token group.

## Service account

The service authenticates to Keycloak as the confidential client `tiko-staff-admin`
(service account `service-account-tiko-staff-admin`). `keycloak/bootstrap.sh` grants it exactly
these `realm-management` client roles:

| Role | Why it is needed |
|---|---|
| `view-realm` | Read `/roles/agent` so an invited user can be mapped to the realm role `agent`. |
| `view-users` | Read a site group's members (`GET /groups/{id}/members`) and a user's groups for the tenant check. |
| `manage-users` | Create users, update their profile/enabled flag, delete them, reset passwords and assign the `agent` role/group. |

It is **not** granted `manage-realm`, `manage-clients`, `view-clients`, `manage-roles`,
`view-events` or any other realm-management role. It cannot edit realm settings, clients,
identity providers, sessions or the role catalogue itself.

The client secret is generated by Keycloak and handed to the service through its own named
volume (`staff-admin-secrets`, file mode 400, owner uid 10002). The gateway mounts only
`gateway-secrets`; the staff-admin volume is not mounted by any other container.

## Authorisation in the service

1. The service validates the caller's access token itself: RS256 signature against the realm
   JWKS, issuer, expiry and the `tiko-api` audience. `X-Auth-*` headers are ignored.
2. The caller must have the `admin` realm role and a `/tenants/{site}` group matching the
   `{site}` path segment.
3. For operations by user id, the target must be a member of that same site group. A user of
   another site answers **404 unknown member**, exactly like a random id, so cross-tenant ids
   cannot be probed.
4. Invitations ignore any role or group fields in the request body: the created account gets
   the `agent` realm role and the caller's site group only.

## Blast radius if staff-admin is compromised

With the service account's token, an attacker can:

- read all realm users and groups (`view-users`) and the realm role catalogue (`view-realm`);
- create, modify, disable and delete **any** user in the realm, not only the caller's tenant,
  because the Keycloak admin API itself is not tenant-scoped;
- reset any user's password and mark it temporary (`manage-users`);
- assign the realm `admin` role to an account, including a newly created one, if the Keycloak
  role-mapping endpoint accepts it for `manage-users`. In that case the attacker can mint an
  administrator for any site and then use the normal APIs.

It still cannot change clients, realm settings, identity providers or the role catalogue's
definitions, and it cannot read the application databases directly. The tenant scoping in
`staff-admin` is the control that keeps a legitimate caller inside its own site; it does not
constrain a stolen service-account token.

Compensating controls today:

- no host port and no external route to `staff-admin`; only the gateway reaches it;
- gateway authentication plus the service's own JWT validation and admin/site checks;
- dedicated secret volume, readable only by uid 10002;
- no persistence: the temporary password is returned once in the invitation/reset response and
  is never written to a file, a database or a log by this service.

For production, narrow the service account further (a custom Keycloak role or Keycloak Admin
API v2 fine-grained permissions scoped to the tenant groups), or replace direct user
administration with a tenant-provisioning workflow that does not hold realm-wide `manage-users`.
